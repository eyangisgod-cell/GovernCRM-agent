## 附录 F：数字员工 / 智能体 / 多智能体协作

### F.1 术语定义（补 PRD 缺口 P-A）

PRD v5.2 全篇只使用"数字员工"一词，第七章标题为"数字员工模型"，7.1 定义其五要素构成。但产品定位（第三章，86 行）写的是「GovernCRM 是**可定制的客户盘活数字员工平台**」，且后续演进必然涉及用户自建员工、一次性任务执行体、多执行体协作。**术语不定义会导致设计返工**——本节冻结三个概念。

| 术语 | 定义 | 生命周期 | 典型用途 | MVP | 首次版本 |
| --- | --- | --- | --- | --- | --- |
| **数字员工（Digital Employee）** | **长期存在、可被反复派发任务的角色实例**。构成 = 角色定义 + 技能包 + 策略包 + 记忆空间 + 自主度等级（PRD 7.1）。**有记忆、积累经验、参与自主度晋级（G1–G4）** | 长（周 / 月） | 沉睡客户唤醒、复购运营、售后关怀、直播推广 | ✅ 单实例（沉睡唤醒专员） | v0.1 |
| **智能体（Agent / Task Agent）** | **一次性、临时的短任务执行体**。**不持有长期记忆、不积累经验、不参与自主度晋级**。**按"使用工具 + 权限"配置**，用完即销毁 | 短（单次任务） | 临时分析、一次性数据核查、即时话术生成、直播实时辅助 | ❌ | v0.3 |
| **多智能体协作（Multi-Agent Orchestration）** | 多个数字员工 / 智能体按**确定性规则**协同完成一个复杂目标。**不是自由群聊**——必须有明确协作拓扑、责任归属与冲突裁决 | — | 如"唤醒专员"产出候选 → "合规专员"复核 → "直播专员"执行 | ❌ | v0.4 |

**一句话区分**：

> **数字员工是"岗位"，智能体是"临时工"。**

**关键澄清（三条，防止后续误解）**：

1. **智能体不是"小数字员工"**。智能体没有记忆空间、不积累经验、不晋级自主度——否则"用完即销毁"的语义无法成立，且会污染员工的长期记忆。
2. **智能体不是治理后门**。智能体产出的任何对外动作**同样必过策略内核**（治理闸门内嵌执行循环是本项目的立身之本）。一次性 ≠ 豁免治理。
3. **多智能体协作 ≠ 多智能体自由群聊**。本项目坚持 single-agent + 强控制面（架构 v5.2 3.1），协作是**受控编排**：拓扑声明式定义、责任唯一、各过各的闸门。

### F.2 智能体（一次性短任务）能力与边界

#### F.2.1 配置维度

智能体的配置面 = **工具 + 权限 + 资源约束**。具体落点复用既有治理构件，不新造体系：

| 配置项 | 含义 | 约束（硬边界） |
| --- | --- | --- |
| **工具清单** | 允许调用的 MCP 工具 / Function Calling 工具 | 取交集：智能体 allowlist ∩ 工具自身声明的 `caller_auth`/`tenant_scope`（架构 v5.2 3.6） |
| **权限范围** | 可读的资源维度、可写的数据范围 | **不得超过发起者权限**（见 F.2.3） |
| **记忆策略** | `none`（默认）/ `task_scoped`（仅本次任务）/ `write_through`（写回主员工记忆） | 默认 `none`；`write_through` 须显式授权且仍过记忆门禁（C10/E13） |
| **预算** | Token / 金额 / 工具调用次数上限 | 不得超发起者剩余预算（单任务 50 万 Token 或 ¥20，裁决 #27） |
| **超时** | 执行时限 | 默认 60s，可配 |

#### F.2.2 智能体 vs 数字员工对照

| 维度 | 数字员工 | 智能体（一次性） |
| --- | --- | --- |
| 记忆 | 有，按员工隔离，长期积累 | **默认无** |
| 经验积累 | 有（技能蒸馏、反思） | **无** |
| 自主度 | L0–L3，参与晋级 G1–G4 | **不参与**，继承发起者约束 |
| 工具权限 | 技能包绑定（经审批） | 创建时冻结，调用时**只减不增** |
| 生命周期 | 长期 | **单次调用即销毁**（仅留审计记录） |
| 治理 | 完整闸门 | **完整闸门**（无例外） |

#### F.2.3 权限放大禁令（不可让步）

> **智能体不得拥有超过其发起者的权限。**

这条与架构 ADR-044「员工级策略覆盖不得绕过抑制红线」同构——**治理红线不可通过任何配置路径绕过**。若智能体能拿到发起者没有的权限，则 RBAC 矩阵（PRD 十一章）被架空。

配套三条：

1. 工具权限取交集，**不取并集**
2. 智能体不获得独立的自主度等级（避免新增一条晋级路径，与 G1–G4 硬标准口径分裂）
3. 智能体的预算计入发起者的预算，不另开额度

### F.3 数字员工演进需求（补 PRD 缺口 P-B/C）

#### F.3.1 内置数字员工与用户创新

| 阶段 | 内置模板 | 用户可创建 | 用户可创新新员工 | 配置界面 |
| --- | --- | --- | --- | --- |
| **v0.1（M1）** | 2 个（沉睡唤醒专员 ✅ 可运行 / 售后关怀专员 ⚠️ 仅模板） | 仅内置模板 | ❌ | ❌ |
| **v0.2（M2）** | 2 个**均可运行** | 内置模板 + **租户自建模板** | ✅ **首次支持**（租户内可见） | ✅ 员工配置页 |

**"创新新数字员工"的最小实现**：租户自建 `worker_template`（角色定义 + 默认技能包 + 默认策略覆盖），实例化后即可派发任务。**不做跨租户模板市场**（需引入模板审核与市场机制，v0.2 过重）。

**待裁决 G-Q1**：v0.2 是否开放租户自建模板 → 建议 **(b) 内置 + 租户自建**。

#### F.3.2 多员工冲突消解（补 v5.2 L13）

> 详见架构 v5.3 附录 E §E.5。本节为需求侧表述。

同一客户、同一时间窗口、多个数字员工的动作候选同时进入派发时：

- **只放行员工优先级最高（`worker.priority` 数值最小）的 1 条**
- 其余 DENY，进"未触达"分析，记录原因 `MULTI_WORKER_CONFLICT`
- **优先级平局 → 升级人工**（不默认放行），规则 ID `ESCALATE_HUMAN`
- 优先级由运营负责人配置，变更走审批 + 写审计；**不设"默认最高优先级"特权**——优先级是业务运营决策

> **与跨平台冲突消解的关系**：跨平台冲突（PRD 附录 D 6 条）处理**同一员工**跨平台的动作冲突；本节处理**跨员工**冲突。两层叠加：**先判跨员工，再判跨平台**。

| --- | --- | --- | --- | --- |

## 附录 G：新增需求条款与异常场景

### G.1 数字员工实体与配置（FR-01 细化，补缺口 P-C）

在 FR-01 之后新增：

| 编号 | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| **FR-01a** | **数字员工实体与五要素配置** | P0 | 系统可持久化数字员工的角色定义、技能包绑定、策略包绑定、记忆空间键、自主度等级五要素（PRD 7.1）；**MVP 阶段仅建数据模型与种子模板，不开放配置界面**（界面随 v0.2，FR-01c） |
| **FR-01b** | **策略包绑定的红线保护** | P0 | 员工级策略包绑定**仅允许覆盖种子 `governance.yaml` 的非红线参数**；任何试图覆盖抑制红线（`SUP_HIGH_VALUE`/`SUP_HIGH_COMPLAINT`/`SUP_HIGH_REFUND`/`SUP_EXPLICIT_REFUSAL`）或 `NO_CONSENT` 的配置**在写入时直接拒绝并给出可操作错误**；**不得通过员工级配置绕过 DENY** |
| **FR-01c** | **数字员工配置界面**（v0.2） | P1 | 运营负责人可在前端创建/编辑数字员工（角色定义、技能包勾选、策略包调整、自主度设置）；**变更留 diff 与审计**；技能包与策略包变更须运营负责人审批；运营专员仅限使用已批准模板创建实例及修改自己名下员工的非治理字段（权限矩阵 a1） |
| **FR-01d** | **跨员工冲突消解** | P0（**v0.2**） | 同一客户同一时间窗口内来自不同数字员工的动作候选，**只放行优先级最高者**（`worker.priority` 数值最小），其余 DENY 并记 `MULTI_WORKER_CONFLICT`；优先级平局升级人工（`ESCALATE_HUMAN`），**不默认放行**；优先级租户内可配，变更走审批 + 写审计。**MVP 单数字员工，此规则在 MVP 不可能触发 → 交付阶段 v0.2**（例外登记见 J.7） |
| **FR-01e** | **用户创新新数字员工**（v0.2） | P1 | 租户可自建数字员工模板（角色定义 + 默认技能包 + 默认策略覆盖），实例化后可派发任务；**租户自建模板仅本租户可见**；内置模板不可删除（仅可停用） |
| **FR-01f** | **RBAC 继承方向单向** | P0 | **管理员不自动蕴含下级权限**：管理员角色不能绕过 REQUIRE_APPROVAL，**更不能绕过 DENY**——管理员只是权限矩阵中的一行，不是闸门的例外分支。DENY 规则对所有角色（含管理员、含 AI、含智能体）一致不可绕过 |

### G.2 API 契约（补缺口 P-D）

| 编号 | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| **FR-38** | **前后端接口契约冻结** | P0 | 全部端点有冻结的请求/响应契约（OpenAPI 入库）；统一响应信封携带 `trace_id` 与**四版本号快照**；错误响应携带 `error.code` + `rule_id`（若来自策略内核）+ `retryable`；**每个 `error.code` 必须映射到某条异常场景 E，或显式登记为非业务错误码**（4xx 认证/参数校验类错误无对应 E 编号），新增错误码须同步登记 |
| **FR-39** | **契约门禁七项** | P0 | ① OpenAPI schema 快照一致；② 契约测试套件全绿（接口签名/字段/错误码/限流行为）；③ 错误码完备性；④ **所有写端点必写审计**；⑤ **所有对外触达端点必过治理闸门**；⑥ **PG 特性集成测试进 CI**（append-only 触发器、哈希链、分区表、CHECK 约束必须用真 PostgreSQL 验证，不得只在内存/SQLite 中跑）；⑦ **必经节点不可 opt-in**（路径完整性断言的检查点不得设计成"调用方自觉调用"，CI 静态扫描须确认执行路径上无跳过分支）——**七项全部进 CI，未过则阻断合并** |

> **与既有条款关系**：FR-09/FR-10 定义的是"模拟 ⇄ 真实"的**系统适配器**契约；FR-38/FR-39 定义的是**前后端 HTTP 接口**契约。两者不是一回事，都需要。

### G.4 新增合规纪律（来自真实工程实践对照）

> **来源**：架构 v5.3 附录 K（真实工程实践对照中提炼的反向约束，ADR-049）。

| 编号 | 纪律 | 理由（附反面案例） |
| --- | --- | --- |
| **C12** | **合规规则、频率规则、抑制规则、权限规则必须落在代码里，不得以 prompt 文本作为唯一实现手段** | 同领域项目把"覆盖策略""跟进频率"写在 prompt 字符串里（`campaign/prompts.py:84`、`sequence_service.py:298-302`）——**Prompt 是 LLM 的建议，不是强制**，Agent 可以不遵守且无人能证明它遵守了。prompt 可以"建议怎么做"，但"不做某事"的保障必须来自代码层闸门 |

## 附录 J：Grilling 决策落盘（2026-10-24 拍板）

### J.1 G-01 · 记忆隔离维度修正

**决策**：(a) 改 PRD 为「租户+数字员工」隔离。

**理由**：MVP 单员工无差别，但 v0.2 多员工时"按角色隔离"会导致 A 员工读到 B 员工的记忆，是真实越权。角色是岗位模板，数字员工是运行时实例——隔离应按实例边界。

**落点**：PRD v5.2 **三处**同时覆盖——
1. §7.1 表格第 4 行「记忆空间」→「按租户 + 角色隔离」**覆盖为**「**按租户 + 数字员工隔离**（每个数字员工独立记忆空间，键格式 `{tenant_id}:{worker_id}`）」
2. FR-06「按租户+角色隔离」→ 同上覆盖
3. §6.2 执行循环表 ·「记忆」行 → 「记忆分租户隔离」**覆盖为**「记忆按租户 + 数字员工隔离」

**覆盖方式**：v5.2 原件**零修改**（版本纪律），本补充章节以**叠加覆盖**方式生效——读 v5.2 原文时必须同时读本条，否则会实现成角色隔离。

**连带影响（须同步实现）**：PRD v5.2 C6「按客户删除记忆」在改为按员工隔离后，需**跨该租户下所有数字员工的记忆空间**执行删除与 `memory_quarantine` 联动清理，不能只清当前员工。

### J.2 G-03 · FR-17 策略工作台置 v0.2
