### 0.2 不可妥协的 5 条红线

```
① policy_kernel.py 是纯函数、零 LLM、零框架依赖、可单测
② DENY 对所有角色（含管理员、含 AI、含智能体）不可绕过
③ 审计 append-only + 触发器拒 UPDATE/DELETE + 哈希链
④ 路径完整性断言：必经节点缺失即 DENY
⑤ 业务层零供应商依赖（CI 扫描强制）
```

**这 5 条任何一条被破坏 = 该任务不算完成**，不论其他功能多全。

### 0.3 两处"假完成"高危点（封板前必查）

| 陷阱 | 表现 | 封板条件 |
| --- | --- | --- |
| **哈希链从未在真数据跑过校验** | 表写了、触发器建了，但字段规范化不一致 → 校验永远失败，或根本没验 | 端到端测试：「改一条记录的 hash → 校验脚本报错并定位到第 N 条」必须通过 |
| **路径断言没真正接进执行链** | `REQUIRED_NODES` / `visited_nodes` 都定义了，但图里没喂进 guard → 断言形同虚设 | 端到端测试：「人为跳过某节点 → 断言 DENY」必须通过 |

> **这两条不能靠"代码写了"验收。** 单测会绿，演示才崩。

## 三、并行开发切分（多 Claude Code）

### 3.1 切分原则

**禁止按技术层切**（前端/后端/数据库）——前端依赖后端接口，无法独立验收，必然互相阻塞。
**按依赖链切**，只并行真独立的项。

### 3.2 并行分组

> **前端（【G】）在 Mock 模式下与后端并行**——只依赖 `ApiClient` 接口定义，不依赖后端实现。`RealApiClient` 骨架保证后续接真 API 时零改动（FD-5）。

### 3.3 并行规则

| 规则 | 说明 |
| --- | --- |
| **Wave 0 必须串行** | 冻结 + 骨架。**骨架没定就并行 = 各自造不同的项目结构** |
| **A/B/C 三路真独立** | B 是纯函数（零依赖，可单跑）；C 纯数据层；A 只产出数据与表定义 |
| **D 之后基本串行** | D→E 有强依赖。**不要试图并行这两个** |
| **F（评测集）可与 E 并行** | 只要 F1/F3 已冻结——标注是纯数据工作。**且标注必须早于内核实现**（T-G1 在 D2，T-B2 在 D3） |
| **G（前端）可与 E/F 并行** | Mock 模式只依赖 `ApiClient` 接口（FD-5），不依赖后端实现 |
| **接口契约先冻结** | E 开始前，先把 `policy_kernel` 的签名与 `Decision` 数据结构定死（B 完成即冻结），G 据此写前端 |

### 3.4 协同机制

| 问题 | 现状 | 处置 |
| --- | --- | --- |
| **`.trellis/` 被 gitignore，worktree 看不到彼此任务目录** | 已知冲突（prd.md 已提出） | **拆解结果额外输出到 `docs/specs/MVP_任务拆解.md`（受 git 跟踪）**，而不是把 `.trellis/` 纳入版本库 |
| **跨 worktree 的接口契约** | 各自看不到 | 契约写入 `docs/specs/`（版本库内），各 worktree 从仓库读 |
| **合并顺序** | — | 严格按 Wave 顺序；每路完成即提 PR，**由主分支统一 rebase 合并**（避免分支并行迁移冲突） |
| **数据库迁移** | 多分支各写迁移会冲突 | **每个 wave 只允许一个分支写迁移**，其他分支只写代码 |

### 5.2.3 适配层设计（FD-5 落地）

```typescript
// web/src/api/types.ts —— 唯一契约，两套实现共用
// 骨架镜像；完整类型定义的权威源 =《GovernCRM_技术架构方案_v5.3_补充章节》附录 N §N.3，
// 两者不一致时以 §N.3 为准（防止双份漂移）。
export interface ApiClient {
  auth: { login(cred: Credentials): Promise<AuthToken>; logout(): Promise<void>; currentUser(): Promise<User>; };
  tasks: { create(...): Promise<Task>; plan(id): Promise<Plan>; confirmPlan(id): Promise<void>; };
  approvals: { list(...): Promise<ApprovalBatch[]>; detail(id): Promise<ApprovalBatch>; sign(...): Promise<void>; reject(...): Promise<void>; forceRelease(...): Promise<void>; };
  decisions: { detail(id): Promise<Decision>; evidence(id): Promise<EvidenceChain>; replay(id): Promise<DecisionChain>; };
  audit: { list(...): Promise<AuditRecord[]>; verify(): Promise<AuditVerifyResult>; tamper(recordId: string): Promise<void>; };
  suppressions: { list(...): Promise<Suppression[]>; summary(...): Promise<SuppressionSummary>; };
  metrics: { workers(...): Promise<WorkerMetrics>; cost(...): Promise<CostMetrics>; coverage(): Promise<CoverageReadiness>; };
  providers: { list(): Promise<Provider[]>; activate(id): Promise<void>; };
  config: { egress(): Promise<EgressConfig>; updateEgress(...): Promise<void>; egressDeclaration(): Promise<EgressDeclaration>; };
  circuitBreaker: { trip(): Promise<void>; restore(): Promise<void>; };
  evals: { summary(): Promise<EvalSummary>; };
}

// web/src/api/index.ts —— env 开关切实现，业务代码只 import 这一个
const client: ApiClient = import.meta.env.VITE_API_MODE === 'mock'
  ? new MockApiClient()   // web/src/api/mock/
  : new RealApiClient();   // web/src/api/real/

export default client;
```

**硬约束**：
- 业务组件**只 import `web/src/api`**，不得直接 `fetch` / 直接 import mock 数据
- `MockApiClient` 的数据来自 `web/src/mocks/snapshot.json`（固定 seed 生成）
- `MockApiClient` **必须实现真实的状态变更语义**（审批签署后列表状态变化、强制放行被拒并返回错误信封、审计篡改返回错误）——**Mock 是数据源替换，不是交互降级**
- 错误响应格式与 `RealApiClient` **完全一致**（统一信封 + `error.code` + `rule_id` + `trace_id`），保证切真 API 时前端零改动

从对照中提炼的**设计约束**（自研实现时必须满足）：

| 借鉴的思想 | GovernCRM 的自研设计 |
|---|---|
| 审批挂起点与工作流解耦 | 审批状态落 PostgreSQL；恢复后**以当前策略版本重新过闸门** |

| 权限继承方向单向 | `system_admin` 不能绕过 REQUIRE_APPROVAL，更不能绕过 DENY |
| 结构化日志三段式 | `module.operation.status` + **额外注入 `trace_id`**（便于关联模型调用） |
| LangGraph 消息裁剪边界 | 自研裁剪函数，覆盖"孤立 ToolMessage"与"无主 ToolMessage"两个 case 并有测试 |
| 测试按依赖分层 | 策略内核标 `unit`（纯函数零依赖，默认进 CI）；**但触发器/哈希链必须用真 PG 验证** |
| OpenAPI 单点生成客户端 | 三态枚举贯穿前后端；契约变更即客户端变更（附录 F §F.4 快照门禁） |
| 迁移与应用启动分离 | append-only 触发器迁移用独立 Job，排在应用启动之前 |
| 一次运行一个可追踪 ID | 一次性智能体每次调用一个 `run_id`（附录 G §G.2） |

**自研时必须规避的三个通用工程陷阱**：
① 日期推算不做字段替换（用 `timedelta`）；② 错误分类用机器可读错误码而非消息文本；③ 治理相关检查一律 **fail-closed**（拿不到数据就拒绝并告警）。

### 9.2 策略一致率三条纪律（G-10）

**策略命中一致率 100%（不可降为 95%）**：

1. **标注先于实现**：标注文件与策略内核分别提交，标注先入库——CI 用冻结标注对照内核输出，杜绝循环论证。**排期上体现为：T-G1 标注任务在 D2，策略内核 T-B2 在 D3**
2. **边界样本 ≥5 条**：20 条含 5 边界样本（三键全平→升级人工 / 频控第3次 / 72h临界 71h59min / 层级分歧抑制侧 / 平台优先级覆盖）
3. **CI 随机抽 3 条人工复核**：每次 CI 跑回放的一致率，额外随机抽 3 条标注结果人工核验

> **口径**：一致率分母 = **20 条策略样本**。5 条路径断言样本独立验收，**不计入分母**（它们验证的是路径断言而非策略判定）。
