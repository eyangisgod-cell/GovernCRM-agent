## 1. 冲突消解 6 条规则表（冻结版）

### 规则 1 · 抑制红线优先

**定义**：任一候选动作的客户命中以下抑制规则 → 直接 DENY，不进入后续规则。

| 红线 | 触发条件 | 动作 |
| --- | --- | --- |
| `SUP_HIGH_COMPLAINT` | 客户近 90 天投诉 ≥1 次 | DENY |
| `SUP_HIGH_REFUND` | 客户近 90 天存在纠纷，**或**退款率超平台阈值 | DENY |
| `SUP_EXPLICIT_REFUSAL` | 客户明示拒绝营销（退订/投诉含"不要再发"） | DENY |
| `SUP_HIGH_VALUE` | 客户消费金额在租户 Top 1% | DENY + 转人工跟进队列 |
| `NO_CONSENT` | 客户无有效营销授权（发送前校验，见规则 1b） | DENY |

> **规则 1a（四红线）** 在分层阶段判定；**规则 1b（NO_CONSENT）** 在发送前校验阶段判定——两者触发时机不同，在 `policy_kernel` 中分两步求值。
> **求值顺序**：四红线与 NO_CONSENT 均命中时，**记录全部命中的 rule_id**，但判定结果同为 DENY。写 `suppression_record` 时按命中列表全量记录，不只记第一个。
> **口径来源**：投诉窗口 90 天、退款条件含"纠纷"——与架构 v5.2 §10.1 抑制红线行一致（此前误写为 30 天 + 2σ，属本冻结版的编造，已改正）。
> **阈值参数化**：`SUP_HIGH_REFUND` 的"平台阈值"由 `governance.yaml` 的 `refund_rate_threshold` 给定（**不做 2σ 统计**——MVP 无足够历史样本做统计阈值，且统计口径不可复现）。评测集直接使用给定的 `refund_rate` 与阈值常量比较。

### 规则 2 · 全局频控

**定义**：同一客户 7 天滚动窗口内全平台合计触达 **≤2 次**（第 2 次合法，第 3 次 DENY）；同一通道两次触达间隔 ≥72 小时。

| 条件 | 判定 | rule_id | 返回值 |
| --- | --- | --- | --- |
| 7 天内触达次数 < 2 | ALLOW | — | — |
| 7 天内触达次数 = 2（本次为第 3 次） | DENY | `FREQ_GLOBAL_7D` | `cooling_remaining_seconds` |
| 同通道距上次 < 72h | DENY | `FREQ_GLOBAL_7D` | `channel_cooling_remaining_seconds` |

> **语义来源**：裁决 #12 原文 "≤2 次"（上限语义），与 FR-19 一致。
> **与架构 v5.2 附录 D 草案的差异**：草案写 "≥2 次 → DENY"，本冻结版按裁决 #12 采 **≤2 语义**（第 2 次合法）。冻结版优先。
> **时间锚点**：所有"距今"判定（7 天窗口、72 小时冷却）以**请求携带的 `now` 参数**为基准；缺省时取服务端当前时间。**评测集必须显式给 `now`**，否则判定不可复现。

### 规则 3 · 冲突窗口排序

**定义**：同一客户多平台候选动作落在同一 72h 窗口 → 只放行优先级最高的 1 条，其余 DENY 并记录原因 `CONFLICT_WINDOW_72H`。

**排序键（三键）**：

```
① 平台局部层级的 layer_score（高者胜）  ← 该候选所属平台的局部层级
② 权益净值（高者胜，按规则 5 折算式计算）
③ 候选创建时间（早者胜）
```

**层级比较式（九宫格 9 层，不可只用三档）**：

```
layer_score = amount_score × 10 + recency_score

amount_score:  high(≥500元)=3 | mid(100–500元)=2 | low(<100元)=1
recency_score: recent(≤30天)=3 | mid(31–90天)=2 | stale(>90天)=1

→ layer_score 取值 11..33，数值大者层级更高
```

**优先级覆盖（最高优先）**：`governance.yaml` 的 `platform_priority_overrides` 若为某平台显式配置了优先级，**该配置优先于三键排序**；未配置的平台才走三键。

> **键①的取值澄清**：架构 v5.2 附录 D 草案写"全局分层层级高者"，但**全局分层是客户级属性**，同一客户的多平台候选全局层级必然相同 → 键①在冲突场景中无法区分候选。故本冻结版明确为**平台局部层级**（全局层与平台局部层各一套，见规则 4）。此为对草案的技术性修正，不改变裁决 #14 的语义。

### 规则 4 · 层级取判

**定义**：同一动作在全局层与平台局部层获不同判定时，**分维度处理**：

| 维度 | 取法 | 说明 |
| --- | --- | --- |
| 权益与资源投入 | 取**更高的 layer_score**（对客户更有价值） | 如全局层 layer_score=23、平台层=33 → 取 33 |
| 抑制与频控 | 取**更严格**一档 | 如全局层 DENY、平台层 ALLOW → 最终 DENY |
| 分层判定 | 取**更严格**一档 | 保守原则 |

**层级比较定义**：全局九宫格与平台局部九宫格**是两套独立层级体系**，各自按 `layer_score`（规则 3）比较。**不存在"全局层级恒大于平台层级"的固定序**——哪一套的 score 更高取决于具体维度值。

> **语义来源**：裁决 #14 原文 "权益与资源投入按更高层级执行；抑制与频控按更严格一档执行"。
> **⚠️ 更正说明**：本冻结版初稿曾写 "全局九宫格层级 > 平台局部层级"，与上表示例（平台判高时取平台）**直接矛盾**。已删除该固定序，改为按 score 比较。

### 规则 5 · 权益取对客户更有利

**定义**：多平台发放不同权益券时，取对客户**更有利**者。

**折算式**：

```
净值 = 面额 − max(0, 门槛 − 客户近 90 天客单价)
净值下限 = 0（负净值视为该券客户不可用，置 0）
```

| 参数 | 默认值 | 配置位置 |
| --- | --- | --- |
| `customer_avg_order_value_window_days` | 90 | `governance.yaml` |

**示例**：客户近 90 天客单价 80 元。A 券（满 100 减 20）净值 = 20 − max(0, 100−80) = 0 元。B 券（满 50 减 15）净值 = 15 − max(0, 50−80) = 15 元。→ 选 B。

> **净值下限为 0**：门槛远超客单价时净值会为负（如面额 20、门槛 300、客单价 100 → 20−200 = −180），负净值无业务含义。置 0 后"两个候选净值都为 0"仍按规则 3 键③（创建时间）裁决。

### 规则 6 · 升级人工

**定义**：前五条无法裁决 → 全部候选挂起，升级人工（E5），记录冲突快照。**不默认放行**。

触发条件：优先级平局（规则 3 三键全相等）、层级无法比较、或其他不可自动裁决的情况。rule_id = `ESCALATE_HUMAN`。

## 3. 评测集标注基准（冻结版）

### 样本构成

| 类型 | 数量 | 内容 |
| --- | --- | --- |
| 简单样本 | 15 条 | 标准场景，规则判定明确 |
| 边界样本 | 5 条 | ① 三键全平 → 升级人工（B01）② 频控恰好第 3 次（B02）③ 同通道 71h59min 临界（B03）④ 层级分歧·抑制侧（B04）⑤ 平台优先级覆盖生效（B05） |
| **合计** | **20 条** | — |

### 标注方式

- AI 按本冻结规则表起草标注 YAML 草案
- eyangisgod 逐条 review（约 30–45 分钟）
- **5 条边界样本建议 eyangisgod 亲自标注**

### 验收口径

- CI 每次跑回放对照：人工标注 vs 内核输出，一致率必须 **100%**
- **每次 CI 随机抽 3 条人工复核**（防止内核被"调成迎合标注"）
- **标注文件与内核分别提交，标注先入库**（防止用内核输出反推标注）

### 标注顺序（不可颠倒）

```
① 本规则表冻结
       ↓
② 人工标注 20 条 → 冻结成 YAML
       ↓
③ 写/调 policy_kernel
       ↓
④ CI 跑回放对照，一致率 100%
```

## 4. 规则 ID 登记表（唯一权威）

> 策略内核、审计流水、评测集标注三处**必须使用同一套 rule_id**。新增 ID 须登记本表。

| rule_id | 规则 | 判定 | 来源裁决 |
| --- | --- | --- | --- |
| `SUP_HIGH_VALUE` | 规则 1a | DENY + 转人工 | #13 / FR-18 |
| `SUP_HIGH_COMPLAINT` | 规则 1a | DENY | #13 / FR-18 |
| `SUP_HIGH_REFUND` | 规则 1a | DENY | #13 / FR-18 |
| `SUP_EXPLICIT_REFUSAL` | 规则 1a | DENY | #13 / FR-18 |
| `NO_CONSENT` | 规则 1b | DENY | #15 / FR-31 |
| `FREQ_GLOBAL_7D` | 规则 2 | DENY（延迟类） | #12 / FR-19 |
| `CONFLICT_WINDOW_72H` | 规则 3 | DENY（被抑制候选） | #14 / FR-20 |
| `LAYER_RESOLVE` | 规则 4 | 记录用（不独立决定判定） | #14 / FR-20 |
| `BENEFIT_MAX` | 规则 5 | 记录用（不独立决定判定） | #14 / FR-20 |
| `ESCALATE_HUMAN` | 规则 6 | REQUIRE_APPROVAL | #14 / FR-20 |
| `PATH_ASSERT` | 路径完整性断言 | DENY | v5.2 §4.4 / FR-25 |

> **禁止自造 ID**：评测集 YAML 中出现的 rule_id 必须在本表内。
> **规则 4 / 规则 5 的 ID 说明**：这两条是**决策过程记录**（记录"层级取了哪套""权益选了哪张券"），**不独立产生 DENY/ALLOW 判定**。它们的 rule_id 写进 `decision.evidence`，但 `conclusion` 由规则 3 的结果决定。因此评测集里 `ALLOW` 的样本可以带 `LAYER_RESOLVE` / `BENEFIT_MAX` / `CONFLICT_WINDOW_72H`（后者表示"另一候选被抑制"），但**`hit_rule_ids` 与 `suppressed_rule_ids` 必须分开记**（见评测 YAML 的 `expected` 字段定义）。
