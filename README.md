# GovernCRM

> **带治理闸门的客户盘活 Agent（数字员工）** —— 每个动作可解释、可回放、可问责；跨平台统一频控，做平台结构性不做的中立层。

**对外统一口径**：MVP 版本使用模拟数据跑通全流程；后续版本接入真实电商平台与企业内部系统数据。

**当前状态**：规划与文档阶段完成（PRD v5.2 + 技术架构方案 v5.2 + v5.3 补充章节），**全部冻结项与设计拍板已于 2026-10-24 完成并落入正式文档**（规则权威源 = `GovernCRM_附录D_冻结版.md`，范围口径 = `MVP_任务拆解.md`），产品代码尚未开工。

> **关键冻结物**：
> - **附录 D 冲突消解规则表**（冻结版）+ 评测标注基准 v1.3 —— 一致率门禁的判定依据
> - **MVP 任务拆解**（范围 + 依赖图 + 10 日排期 + 封板清单 11 项）—— 开发范围的唯一口径
> - 权限矩阵 ⚠️ 脚注 a1–a10 已整包采纳；决策拍板记录属内部资料，不入库
>
> **技术选型的两条防线**（完整论证见内部决策记录，不入库）：
> ① **不复制任何外部项目代码** —— 无论开源或私有项目，只参考模块划分与架构思想，代码一律自研。理由不只是版权：**外部项目的代码带着它自己的隐含假设**，而治理内核的正确性必须能用本项目的验收标准证明

## 这是什么

企业沉淀了大量"沉睡但有价值"的客户：买过一次没回来、咨询未成交、线下老客、服务到期未续。盘活长期依赖人工，存在三个结构性问题——**盘不动**（人力不够，长尾永久沉没）、**盘不准**（靠个人经验，人走经验丢）、**盘不安全**（AI 话术直接群发，重复触达、承诺超权限、出事无法举证）。

GovernCRM 把"沉睡客户唤醒"从人工经验驱动，变成 **Agent 自主执行 + 治理闸门约束 + 经验自动沉淀**：

> **让每个运营都有一队会干活、守规矩、越用越强的数字员工。**

差异化不在"数字员工"这个概念（它已被用滥），而在三个平台与商业竞品**结构性做不了**的组合点上：

| # | 差异化资产 | 为什么别人做不了 |
| - | --- | --- |
| **D1** | **跨平台统一频控 + 冲突消解** | 平台之间是竞争关系，永不互通；SaaS 厂商绑定自家生态——中立第三方位置结构性空缺 |
| **D2** | **决策级审计 + 四版本号回放 + DENY 不可绕过** | 商业竞品的审计停留在操作日志级；"AI 与人均不可绕过抑制规则"可当场验证 |
| **D3** | **"未触达"分析** | 竞品都在展示"发了多少"；本产品展示"**决定不发多少人及为什么**"——平台目标是触达量与 GMV，没有动机展示拦截 |

**关键设计**：治理不是"Agent 之外的另一个系统"，而是**嵌在执行循环里的强制闸门**。Agent 每提出一个动作，必须先过纯代码策略内核（ALLOW / REQUIRE_APPROVAL / DENY）才能执行。

**开源域定位**：经调研核实，目前没有任何开源项目同时具备「CRM 垂直盘活 SOP + 业务语义治理闸门 + 可审计执行循环」——本项目的目标是把这一组合做成开源域第一个可运行、可检索、可引用的参考实现。

## 适合谁 / 不适合谁

| ✅ 适合 | ❌ 不适合 |
| --- | --- |
| 多平台经营（淘系 + 抖店 + 私域并存）的品牌商家 | **仅在单一平台站内经营、无审计要求的中小商家——平台官方免费工具已足够，本项目不适合你** |
| 有线下/存量 CRM、工单数据需融合决策的企业 | 期望"开箱即得真实平台数据"的用户（真实对接需企业主体资质，见[前置条件](#前置条件与合规声明)） |
| 有合规举证与审计要求的品牌方与代运营（TP） | 需要通用 Agent 护栏/多智能体自由协作的场景（本项目只做业务语义层治理，单 Agent + 强控制面） |
| 需要私有化部署与数据主权的组织 | — |

## 核心差异化

| 对比对象 | 它们做什么 | GovernCRM 的差异 |
| --- | --- | --- |
| **电商平台内置工具**（淘天客户运营平台、抖店会员营销等） | 单平台站内自动化触达、复购锁定 | 不正面竞争站内执行（全部复用平台官方通道）；做平台结构性不做的：**跨平台中立频控（D1）、企业侧举证链（D2）、"未触达"透明化（D3）**、内部系统融合决策、经验资产可迁移、私有化 |
| **电商 SaaS / AI 员工**（有赞、微盟、探迹、晓多等） | 闭源 SaaS 托管的"电商数字员工" | 开源可私有化；决策级审计与回放（非操作日志级）；跨平台中立（不绑定自家生态） |
| **通用数字员工平台**（钉钉 AI 助理、百度 Hogee、Salesforce Agentforce、HubSpot Breeze） | 办公协同/全职能数字员工 | 场景不重叠：客户盘活垂直 SOP vs 通用事务；治理带业务语义（知道"高退款客户不能触达"） |
| **Salesforce Agentforce Trust Layer / Trust Map** | 通用 Agent 信任层（横向治理，快速商品化中） | 我们做的是**业务语义层治理**：抑制规则、品类周期、跨平台频控、决策级责任链——通用护栏不重做、复用成熟开源件并预留适配位（A8/ADR-022） |
| **开源 Agent 生态**（编排框架 / 无代码 Agent 管理 / AI CRM 若干） | 编排框架 / 无代码 Agent 管理 / 能力广度型 AI CRM | 有编排无业务语义，或有 CRM 无治理（AI 直写业务表正是本项目定义的失控场景）；本项目 = 垂直业务语义 × 治理闸门内嵌执行循环 |
| **通用护栏开源件**（成熟实现若干） | 危险工具拦截、越狱检测等通用防护 | 互补不竞争：通用护栏直接复用/预留适配位；自研范围严格限定在业务语义层（冲突消解、抑制计量、路径断言、记忆门禁） |

**核心执行循环**（MVP 主链路 = 客户激活自动营销 SOP，15 步）：

```
① 自然语言下达任务 → ② Jev 意图路由 → ③ LLM 规划 → ④ 取数分群 →
⑤ 数据质量门禁 → ⑥ 身份匹配（置信度分级）→ ⑦ 策略内核判定 →
⑧ 跨平台冲突消解 + 全局频控 → ⑨ 内容生成 + 合规审查 →
⑩ 治理闸门（前置路径完整性断言）→ ⑪ 审批责任链（如需）→
⑫ 通道执行（MVP 为模拟发送，幂等 + 回执）→ ⑬ 结果回流 + 记忆写入（过完整性门禁）→
⑭ 复盘反思 → 技能蒸馏候选 → ⑮ 审计写入 + 归因 + "未触达"记录
```

## 治理亮点

| 机制 | 一句话说明 |
| --- | --- |
| **纯代码策略内核** | 决策零 LLM、纯函数、可单测；判定 100% 与规则表一致；**DENY 对所有角色（含管理员、含 AI）不可绕过**，变更只能改规则（走审批 + 回归门禁） |
| **路径完整性断言**（v5.1） | 闸门前校验执行轨迹覆盖全部必经节点（计划校验/合规审查/闸门），缺失即 DENY + 告警——治理链不可被图遍历结构性绕过 |
| **决策级审计 + 回放** | append-only 表 + 触发器拒绝 UPDATE/DELETE + 哈希链校验；四版本号（模型/提示/技能/规则）+ 输入快照，任意历史动作 3 步内还原完整决策链 |
| **记忆完整性门禁**（v5.1） | 记忆写入过 PII 检测 → 注入特征检测 → 来源/可信级别标注；疑似投毒内容拒绝写入 + 隔离 + 告警；高影响决策不得仅凭外部输入级记忆放行 |
| **提示注入防御**（v5.1） | 五道防线：数据/指令分离、受控生成节点、引用强制延伸、闸门兜底、注入样本评测入 CI；外部内容（工具返回/记忆/RAG 片段/客户消息）一律视为数据不作为指令 |
| **第三方推理 API 出境管控**（v5.1） | 出境数据范围显式声明（`compliance/egress.yaml`）+ 一键关闭 + 降级路径须评测验证；**私有化部署默认关闭境外推理 API**，开关变更写审计 |
| **分级自主 + 晋级硬标准** | L0 只建议 → L2 白名单内自动；晋级必须同时满足 G1–G4（≥50 次成功执行 / 修正率 <5% / 评测集全过 / 负责人审批附系统执行报告），G1–G3 系统自动校验；**降级立即生效** |
| **熔断** | 一键停止全部对外动作；恢复语义 = 挂起动作**以当前策略版本重新判定**，不沿用旧判定 |
| **审批责任链** | 按影响面路由；超时不默认通过；绑定申请人/审批人/策略版本/证据快照；v0.2 增批量审批 + 规则候选晋级 + SLA 看板 |
| **失败显式化** | 14 类异常场景全部"禁止静默失败"；审计写入失败阻断业务操作 |
| **MCP 对外只读边界** | 对外暴露默认仅 read 类工具 + 本地 stdio + token 鉴权；write/external_send 一律不对外 |

## 双模型推理链路

> **Jev 负责"这是什么、该走哪条路"，LLM 负责"具体怎么说、怎么做"，代码负责"能不能放行"。**

| 层 | 模型 | 职责 |
| --- | --- | --- |
| 快思考（前） | **Jev 判断模型** | 意图识别、路由、工具选择、合规快检、风险分级——结构化输出，延迟数十至数百毫秒，成本比 LLM 低一个量级 |
| 慢思考（后） | **通用 LLM** | 任务规划、话术生成、复盘反思 |
| 决策 | **纯代码策略内核** | ALLOW / REQUIRE_APPROVAL / DENY——零 LLM、零 Jev |

**工程纪律**（对新模型不跟风、批判性使用）：

- **Jev 置信度只能"向下降级"，绝不"向上放行"**——第三方实测显示其置信度校准不可靠，DENY 权永远在规则内核；
- Jev 不可用/已关闭时不阻塞，自动降级规则路由；中文场景设更低置信度阈值；
- 反思环节**只产出建议，不得自我授权**——改规则必须走审批 + 回归门禁，这是"自进化"与"失控"的分界线。

## 归因就绪

MVP 阶段效果数据为模拟产出，**只给相关性、不承诺因果**（无对照实验不做"复购率提升 X%"式宣称）。但治理设计保证了：

> **审计数据天然支持后续开启归因分析，无需改造。**

每条决策自诞生起就携带完整归因素材——四版本号、命中规则 ID、输入快照、证据链、审批人、模拟回执与"未触达"记录全部 append-only 落库。接入真实平台数据（v0.8）并积累足够样本后，可直接在其上开启对照实验与跨平台归因（FR-34，四维归因、标注相关性），历史架构零改造。

## 明确不做的事

| 不做 | 原因 |
| --- | --- |
| 不做平台爬虫 / 不抓取抖音淘宝公开数据 | 违规且不稳定 |
| 不伪造真实用户数据 | 模拟数据一律打 `_synthetic: true` 标记 |
| 不承诺"复购率提升 X%" | 无对照实验，只能给相关性 |
| 不做站外导流（包裹卡引流、私聊加微信） | 平台检测引流词并降权，2026 年判违规 |
| 不用明文手机号做站外群发 | 淘系/抖店密文与虚拟号机制已关闭该路径；不合法 |
| 不把跨平台归集用于跨平台投放 | 归集仅用于"避免重复打扰"（频控与抑制），不是"把 A 平台客户拿到 B 营销" |
| 不做通用 Agent 护栏（危险工具拦截等） | 已有成熟开源实现，复用并预留适配位；本项目只做业务语义层治理 |
| 不重做平台已有的站内执行能力 | 站内触达、客服、会员权益复用平台官方通道；本产品不拥有通道 |

## 前置条件与合规声明

### 真实数据接入的主体门槛（预期管理）

| 系统 | 门槛 |
| --- | --- |
| 淘宝开放平台 | **2026 起个人开发者禁调订单详情接口**，需企业主体；敏感数据须留在平台云内（聚石塔） |
| 抖店 | 订单/商品接口须**企业或个体工商户**主体；明文不出云 |
| **企业微信** | 客户联系 API 需**企业认证 + 服务商资质**——与电商平台同为主体门槛，**不比电商平台更容易真实接入** |
| 第三方电商数据 API | 可绕开主体门槛但数据合法性存疑（来源可能是爬取或转授权）；**未通过合规评估前一律不启用，默认关闭** |

这就是"MVP 模拟优先"的原因：它不是权宜之计，而是个人开发者在外部硬约束下的**架构资产**——契约先行 + 传输层可替换，真实接入时业务代码 diff 为空（可客观核查）。

### 监管对齐（合规是准入门槛，不是加分项）

| 法规 | 施行/发布 | 本项目的对应设计 |
| --- | --- | --- |
| 《通信短信息服务管理规定（修订）》 | **2026-05-01 施行** | 未经明示同意不发商业短信；授权记录可核查——知情同意（C4）、审批责任链（FR-26）、append-only 审计（FR-27） |

## 研发口径与开源基座

本项目采用"**成熟开源库组合 + 业务层自研**"：

- **库依赖**：编排/检索/API 框架等使用成熟开源库（MIT/Apache 系，见架构方案第十五章清单）；
- **设计参考**：外部项目的设计思想与接口契约**仅作参考，不复制源码**（外部对照明细属内部资料，不入库）；
- **业务层自研**：数据模型（14 张核心表）、策略内核、冲突消解、执行循环、治理层、审计链全部自研——这是项目核心资产，市面上没有现成开源 CRM 携带这些能力。

**许可纪律**：所有引入的第三方组件**动工前必须完成 LICENSE 核对并记录结论**；避免引入带多租户商业条款的修改版许可组件。
